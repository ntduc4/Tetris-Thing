# Tetris AI: build and comparison plan

This is a plan, **not an implementation**. Start with the learning concepts in [LECTURE_NOTES.md](LECTURE_NOTES.md). Goal: compare a strong non-learning MisaMino baseline against neural SARSA, neural Q-learning and, if useful, a separate learned-`V` lookahead baseline under the **same** game interface and evaluation conditions.

## Training runtime (before implementing an agent)

From the repository root, run `make -C tetris_engine ai-setup` once (and again after dependency or binding changes). This installs `tetris_ai/poetry.lock` into a Python 3.14 Poetry environment, builds the local `tetris_py` extension against that interpreter, and runs `tetris_ai/check_env.py`. The check exercises NumPy-to-PyTorch conversion and a GPU forward/backward pass on ROCm, plus a seeded engine reset/lock/respawn; it fails rather than silently training on CPU. Run `make -C tetris_engine ai-check` to repeat the check, then `make -C tetris_engine ai` to open the existing `tetris_ai/train.py` marimo notebook with the binding on `PYTHONPATH`. On ROCm, PyTorch's GPU device name is `cuda`.

The notebook is for prototyping/inspection; keep future long-running, restartable training and checkpointing in scripts rather than relying on a live notebook session. Keep generated checkpoints under `tetris_ai/checkpoints/` and logs under `tetris_ai/runs/` (both ignored by Git). **Passing the runtime check does not mean the placement-level learning environment is ready**: legal placement enumeration, the transition adapter and fair benchmark settings below still need implementation and tests.

## 1. Freeze the experiment contract before choosing a network

- **First task:** solo survival/line clearing, one decision per placed piece, so debugging doesn't mix in opponent policies. Use a 10-column, 40-row engine board, seven-bag, fixed rotation/spin/scoring configuration and explicit top-out definition. Decide whether the metric is lines cleared within a capped number of pieces or survival length; report both. Fix the preview count: the Python default is **5**, while historical MisaMino commonly uses **6**. Give *every* method the same `N` previews (choose `N=5` if the baseline can be restricted, otherwise `N=6` for everyone).
- **Second task:** a separate versus benchmark using fixed attack, garbage, combo, spin, speed and termination rules; do not mix solo scores with win rate. MisaMino's original TOJ-style rule assumptions differ from this engine's approximate TETR.IO-like presets, including rotation and attack tables. Record any rule mismatches explicitly.
- **Time/action model:** initially use turn-based placements with zero gravity and a defined sequence of legal movement/rotation/hold commands ending in hard drop. Explicitly decide whether soft-drop/slide-under/spin paths are allowed. Later, benchmark real-time play with identical frame, input and thinking-time budgets. Versus garbage is tick/delay dependent: either choose a documented zero-delay turn-based protocol or advance the same fixed ticks for both players. Never use a cost-free search/timing exception for just one agent.
- **Information:** only pass the locked board, active piece, hold/hold availability, declared previews, B2B/combo and (for versus) incoming packets/timing, etc. No random seed, RNG internals, future pieces beyond previews, or opponent hidden information as model inputs. Record observed bag history if conditioning on it. Freeze a common observation format, reward, action set and terminal rule in a versioned benchmark config.

Define a transition at piece boundaries: `s = observation with an active piece`, `a = one reachable placement (possibly via hold)`, then execute its **recorded move sequence**, lock, resolve lines/attacks/garbage and spawn; `s'` is the next observation or terminal. If instead training primitive frame-by-frame actions, that is a **different MDP** with far longer trajectories: keep it a separate experiment, not a direct algorithm-only comparison. `γ` applies per **decision/placement** in the first setup, not per keypress.

## 2. Complete and test the environment adapter

Current API in `tetris_engine/apps/python/bindings.cpp`: `tetris_py.Engine` exposes `reset(seed)`, `spawn_next_piece()`, move/rotate/hold/hard drop/tick, `board.render()` (locked cells), `render()` (active piece overlaid), active/ghost piece, queue, hold, counters and garbage. Board row **0 is the bottom**; Python defaults are 10×40 and five previews. `Engine.hard_drop()` does **not** auto-spawn; `SoloSession.hard_drop()` and `Match.hard_drop(index)` do, unless finished. `make -C tetris_engine ai-setup` builds the binding for the Poetry interpreter; `make -C tetris_engine ai` opens `tetris_ai/train.py`.

- [ ] Define `reset(seed) -> observation` and `step(action) -> (observation, reward, terminated, truncated, info)` as a Python adapter, with an explicit episode cap and no training-state leakage. Ensure score/line/attack deltas and top-out are taken from real engine results, not guessed from a board diff. No `paint_cell` or `ignore_hold=True` in gameplay.
- [ ] Implement **reachable legal placement enumeration plus execution paths**, including the exact rotation/kicks, hold gating, spin-relevant last move, soft-drop/slide-under if allowed, and top-out. Deduplicate equivalent outcomes cautiously: equal final occupied cells need not mean equal spin/attack/hold outcome. Validate each enumerated action by replaying its path through the real engine. The declared C++ `generate_active_piece_placement()` / `generate_hold_piece_placement()` currently return empty lists and are not bound to Python. A bare `(rotation, column)` or `ghost_piece` enumeration misses some legal paths.
- [ ] For lookahead and a MisaMino port, add a trustworthy **snapshot/restore or clone** (including RNG/bag, queue, hold, timers, combo/B2B, spin metadata and incoming garbage), or a separate simulator checked against the engine. The Python binding presently has no cloning and doesn't expose arbitrary board mutation for simulation. Never use the held-out true future pieces from a seeded game to evaluate candidates.
- [ ] Tests: same-seed reset reproducibility; board orientation and hidden rows; reachable rotations/kicks/holds; path replay yields the predicted lock, lines, spins, score and garbage; no illegal moves; terminal bootstrap is zero; parity between simulated transitions and live engine. Stress tests for time per placement and batches of games before training.

## 3. Pick inputs/outputs appropriate to the algorithm

**Recommended first model: candidate-scoring `Qθ(s,a) -> one scalar`.** Construct one input per *legal reachable placement*, batch the candidates in PyTorch, and choose `argmax` over that variable-length set. Suggested input: locked-cell occupancy for the **entire configured board** (e.g. a 40×10 binary plane, or color/garbage planes if relevant); one-hot active piece (7), each of `N` preview pieces (7), hold (8 including empty), can-hold; normalized combo/B2B/garbage/timing features if the task uses them; and an action descriptor (hold flag, final rotation/position, execution-path/spin metadata). Optionally add the **predicted post-lock board**, computed only from public state and a validated simulator. Never include a newly drawn piece unavailable at decision time. Normalize continuous counts; use a fixed row convention; mask invalid actions, including after a terminal transition. A compact MLP over engineered features is an easier first debugging target; compare later to a CNN on board planes + an MLP for scalar/action features. Output is an unconstrained value, **not a probability or a move index**. Inputs must carry whatever is needed to distinguish actions with different consequences.

Alternatives to test *after* the first Q run:

| Representation | Output / action choice | Extra requirement |
| --- | --- | --- |
| Fixed primitive-action `Qθ(s) -> 8 scores` | Mask illegal left/right/soft drop/three rotations/hold/hard drop; choose a command each step. | Frame/tick model and many more transitions; not directly comparable to placement-level Q without a separate protocol. |
| State value `Vφ(s) -> one scalar` | Score each legal action by estimated `r(s,a) + γ E[Vφ(s') | s,a]`, or use a sampled/specified next-state distribution. | Accurate successor simulation and handling unseen future pieces. Train `V` by TD/MC; **V alone is not SARSA or Q-learning**. |
| Policy (or policy + value) | Score/legal-action probabilities, optionally a value head for search. | Different algorithm (e.g. imitation, actor–critic/PPO); not needed to answer SARSA vs Q-learning first. |

## 4. Train controlled baselines, then neural agents

1. **Sanity checks:** random-legal policy, simple handcrafted board evaluator (holes/height/roughness/line opportunities) and toy tabular TD update tests. If these fail, do not spend GPU time. Use an identical legal-action generator and deterministic tie-breaking for all agents.
2. **Neural SARSA and neural Q-learning:** same candidate Q-network, optimizer, input encoding, reward, `γ`, training seed distribution/sample budget and exploration schedule. For each nonterminal transition, use a common prediction `Qθ(s,a)` and squared/Huber TD error, but different detached targets: SARSA `r + γ Qtarget(s', a'_behavior)` where `a'_behavior` is the next ε-greedy action **actually executed**; Q-learning `r + γ max_{b legal} Qtarget(s',b)`. At terminal, both targets are just `r`. Keep target-network updates consistent. Start SARSA with on-policy online/fresh-rollout updates; reusing an old replay buffer while the behavior policy changes is **not automatically on-policy**. A DQN-style target network/replay is an engineering extension, not a guarantee from the slides; if Q-learning alone later gets replay, report that as a separate ablation.
3. **Reward experiment:** choose a primary objective *before* training (e.g. survival length plus lines in solo, or win/loss in versus). Log the actual game outcome. Try a fixed reward with explicit death penalty and line/attack bonuses; separately ablate shaping for holes/height. Potential-based shaping `r' = r + γ Φ(s') - Φ(s)` with `Φ(terminal)=0` is easier to reason about than arbitrary per-step penalties. Do not compare agents trained toward different rewards as if only their algorithms changed; report game metrics regardless of reward.
4. **Optional `V` baseline:** train `Vφ` with TD or complete-episode returns, then use the *same* reachable actions and simulator to rank `r + γ E[Vφ(s')]`. Match lookahead and simulation budget to the MisaMino evaluation or explicitly report extra runtime. A dual-head `V/Q` model is an optional later ablation; Q targets still define whether training is SARSA or Q-learning.
5. **Optional teacher:** once MisaMino is working, collect expert `(s,a)` labels; behavioral cloning can initialize a policy/Q scorer and DAgger can query the expert on learner-visited states. Evaluate a pure imitation baseline separately from any imitation-pretrained RL agent to attribute gains honestly.

## 5. MisaMino as a genuine baseline, not a different game

Original project: <https://github.com/misakamm/MisaMino>. An existing command-line adaptation is <https://github.com/jezevec10/MisaMinoBot> (its README describes a state/field input protocol, but its example output is the *resulting field*, not a directly replayable move sequence; integration needs more work). MisaMino is a search/heuristic Tetris bot with hold/lookahead and T-spin-aware play, **not** a neural RL algorithm. The original repository's `LICENSE` only says “Copyleft by Misakamm”; check permissions and any derivative's license before copying or distributing source. Keep attribution and a pinned version/commit. A reimplementation should be labeled **“MisaMino-inspired”**, not an exact port, unless behavior has been verified.

- [ ] Choose either (A) port/adapt the original decision logic to take the shared observation and return a legal action/path in **this** engine, or (B) independently reimplement its documented search/evaluation strategy with attribution. Record search depth/width, preview limit, hold policy, style, weights and compute budget; do not claim parity without differential tests on known positions.
- [ ] Adapt piece identity, coordinate origin, hidden rows, 7-bag and queue, rotation/kicks/180, hold, spin detection, combos/B2B, attack/garbage/cancellation and top-out. Revalidate selected moves and outcomes in the shared engine. If the original rules cannot be matched, label native-MisaMino runs **cross-rules reference only**, not head-to-head evidence.
- [ ] Fix an equivalent information limit and per-decision time/number-of-node-expansions budget for search agents; record both strength-vs-time curves and unconstrained results separately. A deep lookahead baseline can beat a one-ply learned policy partly because it gets more computation; report this tradeoff rather than hiding it.

## 6. Evaluation and decision gates

| Gate | Required evidence |
| --- | --- |
| Environment ready | Seed repeatability; all enumerated paths legal and replayable; no future leakage; simulator agreement on spins/attack/top-out; defined truncation. |
| Learning ready | Tutorial 5 tabular target check (2.12 vs 2.44); tiny synthetic/overfit test; better-than-random solo performance across *held-out* seeds. |
| Baseline ready | MisaMino move adapter produces legal replayable placements; settings, license/provenance and any rule differences documented. |
| Comparison ready | Frozen rules/reward/seeds and reporting script; separate solo and versus tables with uncertainty and runtime. |

Use independent training/validation/**held-out test** seed lists, multiple training seeds for each neural method and the same test seeds for every agent. For solo, report median/mean lines and pieces before top-out, top-out fraction and lines per piece at a **fixed piece cap** (mark episodes that survive the cap as truncated, not deaths). For versus, play paired matches with seat/order swaps, identical information and speed rules; report wins/draws, attacks sent/received, attack per piece and survival, with confidence intervals. Log learning curves versus environment placements **and** wall-clock/GPU time; inference latency and search nodes per decision matter too. Compare SARSA vs Q-learning first under matched architecture/sample budget; compare their strongest validation-selected checkpoints with MisaMino on held-out tests at stated information and runtime budgets. Avoid selecting a winner on the test set.

**Implementation order:** shared experiment contract → legal-path adapter and tests → random/heuristic baselines → matched Q-network SARSA and Q-learning → pinned MisaMino port/reimplementation and parity tests → held-out solo comparison → versus benchmark → optional V/lookahead, DAgger and real-time variants. Do not start with PPO/actor–critic: their dedicated lecture is missing here, and they answer a different comparison question.
